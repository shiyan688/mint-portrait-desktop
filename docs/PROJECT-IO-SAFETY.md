# Manual project file safety (development candidate)

The project format is `.mintproj`. It embeds the original compressed JPEG/PNG/WebP bytes, settings, bounded undo/redo snapshots, immutable learned planes and their provenance, and separate manual correction strokes. It is **not an image export** and contains original image data, potentially including original metadata. Treat it as private; share it only with intended recipients. There is no automatic upload, cloud save or project encryption. This page describes explicit user-selected project files, which are not automatically overwritten. The separate optional local recovery store is disabled by default and described in RECOVERY-STORE.md / RECOVERY-DESKTOP.md; it contains the same private original-photo data in fixed host-owned locations.

## Authority and verification

Only native Electron open/save dialogs select paths. The renderer cannot supply a read/write path, and embedded project metadata never grants filesystem authority. Main-process handlers use the same exact-origin/main-frame IPC checks as image export. Save freezes the incoming bytes before asynchronous work, then independently decodes/verifies the container. Open checks extension, ordinary-file type, byte count and immutable read identity before decoding. It preflights the fixed64-byte framing header against actual file size before allocating the full file buffer. Symlinks and directories are rejected. The codec verifies version, metadata and blob hashes, references, bounded dimensions/history, alpha ranges and source identity. The renderer must also successfully stage image previews/thumbnails before replacing the current session.

A selected existing target must itself be a valid decodable project. Unknown or corrupt existing files are not overwritten: choose a different new filename. Original image file extensions are never accepted for saving projects. No original image file is rewritten.

## Commit and failure handling

The writer creates a uniquely named exclusive temporary file in the selected directory, writes bounded chunks, flushes the file and closes it. Before commit it checks whether the destination changed since validation. For a new destination, atomic hard-link creation provides no-replace semantics, followed by removal of the temporary name. Filesystems without hard-link support cannot create a new project through this writer; the operation fails rather than switching to a partial-write or overwrite-prone fallback. For an existing validated destination, the commit is same-directory atomic rename. There is **no** delete-old/copy fallback if rename or linking is unsupported or fails.

Pre-commit write, flush, cancellation or destination-change failures retain the old project and remove only this operation's temporary file. Cancellation from a native dialog performs no save. Directory-flush failures after a successful commit are reported explicitly as a durability warning, not as if the old file were restored. Windows uses file flush + atomic replacement; native Windows lifecycle and power-loss durability have not been tested. Actual guarantees depend on the filesystem. There is no cross-process transactional compare-and-swap for replacing an already-existing file: a narrow external-writer race remains after the final check. Do not have two applications save to the same project simultaneously.

A process or machine crash before commit can leave the exclusive temporary file alongside an intact old project. It is never auto-opened or silently adopted. The separate opt-in recovery store now maintains two fully validated candidate generations, with explicit restore selection; it does not promise zero-loss crash/power-loss recovery or adopt these manual-save temporary remnants. Closing the application is refused while a project dialog/validation/write is active; the user can cancel the native dialog or wait for the operation.

## Limits and tested evidence

Original compression and dimensions are preserved independently of preview decoding. This milestone does **not** remove the current 4096-long-edge / 16-million-pixel processing/export cap, introduce RAW/16-bit/color management, or package new model runtimes. Embedded projects can be large and require substantial memory for validation and IPC. The schema limits are enforced by `src/project-document.cjs`; the main process checks maximum bytes before allocating a file buffer.

`tests/project-store.test.cjs` runs actual local filesystem saves/opens and injected failure cases. Electron dialogs are mocked. It verifies exact bytes, cancel, wrong extensions, corrupt target rejection, bounds before reading, symlink rejection, write/flush/rename failures, abort cleanup, destination changes, no-clobber new-file races, post-commit durability reporting and serialization. It is not native Windows or real browser evidence.
