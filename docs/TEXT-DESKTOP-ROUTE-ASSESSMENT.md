# Desktop editable text: historical route assessment

Assessed 2026-10-22 UTC.

Implementation note: the subsequent source increment chose8 editable layers, a bounded rawRGBA envelope, and the existing single-stage export request. It does NOT implement the proposed two-phase token/PNG path below. Current contracts are TEXT-LAYERS-CONTRACT.md, TEXT-RASTER-RENDERER.md and TEXT-DESKTOP-UI.md. This historical assessment records alternatives, not installed features. This is a design/feasibility checkpoint, not shipped text functionality. No production, padding, dependency, packaging or mobile source was changed.

## Decision

Use the **existing sandboxed Electron renderer's Canvas for all text measurement and rasterization**, then pass a bounded transparent PNG to the existing native Sharp worker for source-over composition and final PNG/JPEG encoding. Sharp must not measure text, render SVG text, substitute fonts, or resize the text layer. This requires no new runtime dependency, font download, browser service or security change.

Keep the shared `text-overlay.js` byte-identical: SHA-256 `44874197cdf371f6763228d61a67c75346c50e37c2267e2b9e69e33f314f93a1`. It already validates the complete recipe, measures at canonical short-edge 1024, wraps graphemes, and renders with Canvas. Its source is the sibling mobile checkout's `app/src/main/assets/text-overlay.js`; behavioral contract: `docs/TEXT-OVERLAY.zh-CN.md` there.

Using it in production would require acquiring/verifying that artifact, recording a lockfile, extending the Windows staging/unpack list, and executing a Windows/Electron integration test. Copying the Linux module or depending on this cloud's absolute `NODE_PATH` is not a distributable solution. Its font resolver also need not match Chromium's, even though both use Skia. [Official package source](https://github.com/Brooooooklyn/canvas).
- An Electron 45 Windows x64 archive is already cached (158,223,852 bytes), and `.build/win-deps` already contains the Windows Sharp module. That supports existing packaging inputs, **not a runnable Linux Electron or a Windows launch result**. The desktop `node_modules/electron` here has no installed `dist` runtime.
- Prior **npm-command denial** remains in force, independently of the user's general dependency authorization. No npm/install command, alternate installer, direct archive-fetch workaround or network execution was attempted. The denial's original details were not recovered from private logs; repository QA records corroborate that the restriction exists.
- Prior normal-sandbox Chromium socket startup and supported-browser `file:` navigation failures remain in force. See `docs/EXPORT-LAYERS-OCT22.md` and `docs/MANUAL-TOOLS-DESKTOP.md`. No browser retry, local server, sandbox weakening, user-machine route, credential, model or API was used. These block native browser acceptance, **not writing and testing the protocol/pixel/state integration**.

Electron's sandbox has no Node environment in the renderer. Preserve `sandbox:true`, `contextIsolation:true`, `nodeIntegration:false`, existing `mint://` origin/network restrictions, and exact sender/main-frame checks. Expose narrow preload methods, not `ipcRenderer` or filesystem access. [Electron sandbox contract](https://www.electronjs.org/docs/latest/tutorial/sandbox).

## Smallest implementation contract

1. **Own a recipe, not a flattened preview.** Start with one optional editable paragraph per photo, stored as a complete validated recipe in settings/history/project. Absent recipe is identity; missing core or malformed saved recipe fails closed. Bump the project schema and test migration explicitly. Do not import mobile's operation-log/edit-latest semantics into desktop settings accidentally. Placement is relative to the **final canvas after crop/rotation/flip and padding**; subsequent geometry changes reflow/reposition the paragraph in that final coordinate space. State this in the UI. Text is not a global color preset or automatic cross-photo sync setting.
2. **One font engine and one final-size text surface per export basis.** Calculate the exact native output plan first. Call the unchanged core's `render(ctx, finalWidth, finalHeight, recipe)` on a fresh transparent sRGB Canvas, with system `sans-serif`/`serif`/`monospace` only. For accepted preview, scale this finished text raster onto the existing accepted image preview; do not measure again at rounded preview dimensions. Original versus working-size processing can quantize fractional crop/padding differently and produce slightly different final aspect ratios. Therefore label the preview's current `mode + finalWidth + finalHeight` basis; changing export mode invalidates/regenerates the overlay and refreshes that preview. Strict equal line breaks apply only to preview/export sharing the same basis, **not automatically across all export sizes**. Use the same raster for the current export when its complete snapshot matches, otherwise regenerate from the frozen queued recipe. Final export never enlarges the preview bitmap.
3. **Publish atomically.** Render into a disposable canvas; publish only after successful validation/render and a complete snapshot/current-generation check. The accepted composite, not a decorative DOM layer, must feed the existing reference capture and pixel inspector. Do not alter original pixels or an accepted canvas on failure. Debounce text edits and reject stale preview completions; draft, undo/redo, project replacement and queue freezing must use existing photo ownership/revision locks. Do not mutate/reset a surface still being encoded or consumed.
4. **Prepare, then consume one job.** Extend the export service with a preparation stage: main validates/clones source bytes, settings including text, analysis and exact output plan, reserves its existing single active slot, starts the timeout, and returns a main-minted single-use token plus the authoritative dimensions/validated text snapshot. Keep the prepared request in main. Bind the token to the calling trusted webContents/main frame, `requestId`, source revision, full frozen recipe/settings and plan, rather than accepting replacement settings at completion. `renderExport({token, overlayBytes})` consumes that prepared job once. No text uses the current path unchanged.
5. **Transfer bytes, not DOM objects.** Renderer waits for local `document.fonts.ready`, generates the prepared final-size surface, encodes `image/png`, checks Blob size before `arrayBuffer()`, and sends an exact-length `Uint8Array`. No base64, SVG, paths, URL, Blob, ImageBitmap or raw full-photo return trip. `invoke` uses structured cloning; do not describe this as zero-copy. Copy validated exact-sized bytes once into worker-owned storage and use the existing Node worker transfer list. Reject unexpected fields, offset/oversized backing buffers, shared/resizable/detached storage and duplicate tokens. [Electron IPC serialization](https://www.electronjs.org/docs/latest/api/ipc-renderer).
6. **Validate and composite natively.** Main checks the prepared dimensions, PNG signature/header and APNG exclusion before dispatch. Worker independently decodes under the text pixel/edge limit, rejects wrong size/pages/channel contract, converts to sRGB RGBA and composites at `(0,0)` using source-over **after existing pixel operations, framing and padding**. Never resample the layer. Scrub hidden RGB after the final composition, then retain existing white JPEG flattening, sRGB profile, output-byte cap and atomic file write behavior. Do not start writing on an invalid/missing active-text overlay.

The token validates **job ownership and the renderer's declared recipe association**, not mathematical proof that an arbitrary submitted PNG contains those glyphs. The trusted local renderer owns the text renderer; main/worker own source pixels, dimensions, bounded composition and encoding. A recipe hash alone is not pixel attestation. If independently re-rendering/attesting untrusted renderer text is required later, this architecture must change rather than claiming its validators already establish that.

### Concrete schema and session binding

- Proposed persisted field: `settings.textOverlay: null | TextRecipeV1`; use the shared core's exact fields, without an embedded bitmap, font path or font bytes. Padding currently writes project v8, so reserve the next schema revision for this addition; older projects migrate to identity. Undo/redo stores whole validated recipe snapshots. Export basis is UI/queue state, not a new coordinate interpretation inside the portable recipe.
- Proposed preload surface: `prepareTextExport(payload)`, existing `renderExport(completion)` with a strict tagged prepared-text variant, and existing `cancelExportRender(requestId)`. `prepareTextExport` accepts the same complete source/settings/analysis/mode/format/quality request currently validated by native export. Main returns `{protocol:1, token, requestId, snapshotHash, textBasis:{mode,width,height}, text, limits:{pixels,edge,pngBytes}}`. Main retains the immutable request and the trusted sender/frame generation. Token is unpredictable, single-use and distinct from the diagnostic hash.
- Main computes `snapshotHash = SHA256(canonicalSnapshot)`: canonical protocol version, source-byte SHA-256, source revision, full validated settings, analysis digest, mode, format, quality, exact native plan and frozen text-core SHA-256. Canonicalize sorted own plain-data keys; encode typed analysis buffers by type/dimensions/byte digest, not ad-hoc JSON of a typed array. Do not trust a renderer-supplied hash as the authoritative snapshot. Renderer preview ownership additionally checks photo/Blob identity, settings generation and its accepted view token.
- Completion is exactly `{protocol:1,token,requestId,snapshotHash,overlayBytes}`: it cannot replace source, recipe, mode or plan. Main verifies job association, computes `overlaySha256`, validates the bounded PNG, and transfers `{...frozenRequest,textOverlay:{snapshotHash,overlaySha256,width,height,bytes}}` to the native worker. Worker/result envelope carries the same hashes; main validates them and the existing encoded output dimensions before returning success. Store no tokens, raster buffers or session hashes in the project. Hashes prevent accidental association drift, not a malicious renderer's alternate glyph bitmap.

### Cancellation and staleness

- Preparation is busy from reservation onward, including font wait and Canvas PNG encoding. Existing native close guards must see it. Cancel, timeout, navigation, renderer destruction and process failure invalidate the token and release held data; completing a canceled job cannot create a worker or write a file.
- Register cancellation before preparation, recheck after every await, and cancel a late successful preparation explicitly. Canvas synchronous drawing/PNG encoding may not be interruptible mid-call: cancellation prevents publication/dispatch and discards the eventual result; it is **not** a promise of immediate CPU interruption.
- Once dispatched, existing worker termination continues to stop native processing. Clear late callbacks and prepared storage once. A new job must not receive an old job's surface/result. Queue retries retain the frozen recipe and never repeat already-saved items. Existing write-commit uncertainty rules remain unchanged.

### Explicit budgets, not a memory claim

For the smallest first milestone, recommend **active text final canvas ≤16,000,000 pixels and edge ≤16,384**, with transparent overlay PNG ≤32 MiB. Original source remains subject to current 64,000,000-pixel import/native-plan limits and source/output files remain ≤80 MiB. No-text export retains its existing 64,000,000-pixel allowance. Check the text limit after all framing/padding; reject over-budget text visibly or let the user explicitly choose working-size export, never silently downsample. Source processing can still require more memory than the final cropped image.

Each 16MP RGBA surface costs 64,000,000 bytes (~61 MiB). Own at most one full-size text surface per active operation and process the export queue serially; drop the preview text cache before allocating an unrelated queue surface. Encoded Blob, structured-clone copies, decoded overlay, source pixels and Sharp buffers add to this, so the limit is an allocation gate, **not a proven total-RSS bound**. Node's `resourceLimits.maxOldGenerationSizeMb` does not cap all native/ArrayBuffer/Canvas storage. At the existing 64MP ceiling one text surface alone is 256,000,000 bytes; do not advertise that text capacity until native peak-memory/cancellation tests support it.

Same-renderer/system-font text geometry is the promised consistency. Generic fonts/emoji can vary across OSes, and scaled display pixels, alpha rounding and PNG/JPEG encoders do not imply preview/export or cross-OS pixel equality. A frozen full-size raster avoids a second text-layout implementation, not these normal raster/codec differences.

- An in-memory synthetic 600×800 check rendered mixed Chinese/Latin/combining/emoji text with opacity/outline/shadow/rotation through the frozen core and installed Canvas, then passed its 32,834-byte PNG into installed Sharp source-over composition and PNG/JPEG encoding. Dimensions and source bytes were retained; 153,802 opaque pixels outside the layer were exact; text added alpha at 6,201 initially transparent pixels; opaque source-over color differed from the scalar rounding oracle by at most 1 code value. No file, portrait or font was downloaded. This demonstrates the raster-to-native compositing interface, **not Electron IPC, actual Chromium font output or integrated UI**.
- Existing `quality/reference-compare-qa/INDEPENDENT-REPORT.md` documents a conditional Canvas 0.1.100 snapshot/PNG discrepancy. Do not promote QA-library readback to universal Canvas/browser acceptance or package that dependency merely because these focused text checks passed.
